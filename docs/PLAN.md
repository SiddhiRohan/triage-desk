# Triage Desk: build plan

This is the spec the orchestrator works from. It says what to build and the rules it has to follow.
It does not say how to write the code. That is the builders' job.

## What it is

A small intake router. Messages come in, each one gets a category, a priority and a confidence
score, and lands in a queue. Anything below the confidence threshold goes to a "Needs human" queue
and sits there until a person looks at it. The router never sends, closes or deletes anything.

## Stack

- Python 3.12, FastAPI, SQLite (one file, `data/triage.db`), plain HTML + a little vanilla JS
- One process: `uvicorn app.main:app`, serves both the JSON API and the board page
- Classifier calls Ollama Cloud through its OpenAI-compatible endpoint (`https://ollama.com/v1`),
  model name read from `TRIAGE_MODEL` env var, API key from `OLLAMA_API_KEY`
- No frameworks on the front end. No build step. No Docker for the app itself.
- Tests with pytest. They must run offline (mock the model call).

## Layout

```
app/
  main.py        fastapi app, routes, serves the board
  db.py          sqlite schema + helpers
  classify.py    llm call + keyword fallback + the queue runner
  rules.py       keyword fallback classifier (no network)
  static/
    board.html
    board.js
data/
  feed.json      the synthetic messages (checked in)
  triage.db      created at runtime, git-ignored
tests/
scripts/
  run_feed.py    loads feed.json, classifies one at a time, saves results
```

## Data model

table `messages`
- id (text, from the feed), subject, body, sender_name (fake), received_at

table `decisions`
- message_id, category, priority, confidence (real 0..1), reason (one line),
  queue, source ("llm" or "rules"), model, decided_at

table `audit`
- id, message_id, action, detail, at. Every routing decision writes a row. Re-routes would too.

## Categories, priorities, queues

- category: one of `support`, `billing`, `bug`, `sales`, `other`
- priority: one of `low`, `normal`, `high`
- queue: `Support`, `Billing`, `Bug`, `Sales`, `General`, `Needs human`
- queue = "Needs human" when confidence < `CONFIDENCE_THRESHOLD` (env var, default 0.70),
  otherwise queue follows category (other -> General)

Why 0.70: the feed has a handful of deliberately vague messages. On a 30 message feed, a 0.70 cut
should send roughly 4 to 8 of them to a human. If it sends 0 or 20 the threshold is wrong, and
DELIVERY.md should say what we saw and why we landed where we did.

## The classifier

1. Build a short prompt: the message, the allowed categories and priorities, ask for JSON with
   `category, priority, confidence, reason`.
2. Call the model. One message at a time, never in parallel (Ollama free plan = 1 concurrent).
3. Parse the JSON. If it fails to parse, retry once with the parse error in the prompt.
4. On HTTP 402 or 429, or any network error, or a second parse failure: use `rules.py`
   (keyword match) and cap its confidence at 0.5 so the item goes to Needs human. Record
   `source = "rules"` so the board can show it.
5. Save the decision and an audit row.

`scripts/run_feed.py` runs this over the whole feed and is idempotent: a message that already has a
decision is skipped.

## The board

One page at `/`. Columns (or sections) per queue. Each card shows subject, category, priority,
confidence. Click a card -> a panel with the body, the reason, source (llm or rules), model, time.
Needs human items are visually different and have no action buttons at all.

API the page uses:
- `GET /api/messages` -> all messages with their decision and queue
- `GET /api/messages/{id}` -> one, with the audit trail
- `GET /api/config` -> the threshold and model name, so the page can show them

## Hard rules (the reviewer checks every PR against these)

1. No code path sends email, calls a webhook, closes, deletes or modifies a message. Grep for
   `smtp`, `requests.post`, `httpx.post`, `DELETE` routes, `send`. The only outbound call is the
   classifier to the model API.
2. Items under the threshold are never auto-routed anywhere except Needs human.
3. No real or personal data in the feed. Names, emails, companies are all invented.
4. Secrets come from env vars. Nothing in the repo contains a key.
5. Tests run offline.

## Synthetic feed

30 messages in `data/feed.json`. Roughly: 8 support, 7 billing, 6 bug, 5 sales, 4 vague on purpose
(half a sentence, mixed topics, or nothing actionable). Each has id, subject, body, sender_name,
received_at. Generated by a builder agent, not by hand.

## Definition of done for the whole thing

- `uvicorn app.main:app` starts with an empty db, `scripts/run_feed.py` fills it
- the board loads at `/` and shows every message in a queue
- clicking an item shows its decision
- at least one item is in Needs human
- `pytest` passes
- the hard rules hold

## Tickets I expect the orchestrator to produce

It should break the above into 6 to 8 GitHub issues, each with: a title, which agent it goes to,
what files it touches, and acceptance criteria. Roughly:

| # | Title | Agent | Acceptance |
|---|---|---|---|
| 1 | Project skeleton: FastAPI app, sqlite schema, pytest wiring, README run instructions | builder-core | app starts, `GET /api/config` returns the threshold, one passing test |
| 2 | Synthetic feed: 30 messages in data/feed.json | builder-core | counts per category roughly as above, 4 vague ones, no real names, valid JSON |
| 3 | Keyword fallback classifier (rules.py) | builder-core | pure function, returns category/priority/confidence <= 0.5/reason, tests cover each category |
| 4 | LLM classifier + queue runner + run_feed.py | builder-core | one at a time, JSON parse with one retry, falls back to rules on 402/429/error, idempotent, tests mock the model |
| 5 | Board page + messages API | builder-ui | page lists every message by queue, click shows decision, Needs human has no action buttons |
| 6 | Audit trail + config endpoint | builder-core | every decision writes an audit row, `GET /api/messages/{id}` returns it |
| 7 | Test pass: the hard rules | tester | tests that assert low confidence -> Needs human, board lists all messages, no send/delete code path (grep test) |
| 8 | Deploy: Caddy on port 80, systemd unit, run_feed on boot | builder-core | public URL loads the board |

Order matters: 1 -> 2 and 3 in parallel -> 4 -> 5 and 6 -> 7 -> 8. The reviewer looks at every
PR before merge. The tester runs after 5 and 6 are in. Anything the reviewer or tester bounces
goes back to the builder with the reason on the issue.

Optional, only if tokens and time are left after 8: `POST /api/intake` that classifies one new
message and shows it on the board. Useful for the live demo in the follow-up call.
